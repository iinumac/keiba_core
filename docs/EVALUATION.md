# 再現評価の手順（過去の開催日を「当日の朝に予想した」として評価する）

いまの予想ロジック（`keiba.views` と `keiba.flags`）が実際のレースでどれだけ当たるかを、
開催日ごとに確かめるための手順。人がやっても AI エージェントがやっても同じ手順で、同じ形の
結果が出るようにしてある。

## 何をするか

1. 開催日を1日ずつ再現する（`scripts/replay_day.py`）
   - その日より前のデータだけで、全レースの目線・ピックアップ・要注意を出す
   - 実際の着順を並べたレポート `reports/<日付>_views.md` と、集計用の
     `reports/data/<日付>_views.csv` を書く
2. 何日分かをまとめて集計する（`scripts/summarize_replays.py`）
   - `reports/SUMMARY.md` に日ごとと合計の成績を書く
3. 結果を読んで報告する（下の「結果の読み方」）

## 前提

- 作業場所はリポジトリの直下（`keiba_core/`）。Python 3.9、依存は導入済み
- `colab`（google-colab-cli）がインストール済み（`~/.local/bin/colab`）でログイン済み。
  `colab sessions` が通れば使える。通らなければ、人にログインを頼む（認証コードを扱うのは人）
- 学習済みモデル `models/model_strategy.pkl` と `models/model_free.pkl` があること

## 手順

```bash
cd keiba_core
python3 scripts/replay_day.py 2026-10-11     # 1日ずつ。土日なら2回
python3 scripts/replay_day.py 2026-10-12
python3 scripts/summarize_replays.py         # 何日分でもまとめて集計
python3 tests/test_pipeline.py               # 何かを変えたときだけ。最後に「✅ すべて成功」
```

`replay_day.py` が自動でやること：

| 状況 | 動き |
|---|---|
| その日の結果がウェアハウスに無い | Colab 経由でレースのHTMLを取り、手元でパースして取り込む（`stages.collect` / `stages.build`） |
| 出馬表の控え `reports/data/<日付>_cards.json` が無い | Colab 経由で出馬表と確定オッズを取り、控えに保存する |
| 控えがある | netkeiba には行かず、控えを使う（作り直しは何度でもしてよい） |

1日（24レース前後）で20〜25分かかる。ほとんどは手元の計算で、netkeiba へのアクセスは
1日あたり50回程度。2日分を同時に（別プロセスで）回してもよい。

## 守ること

- **netkeiba に手元の端末から直接アクセスしない。** 手元のIPは制限されたことがある。
  取得は必ず `keiba.colab_remote`（Colab の VM）を通す。`keiba.fetch.Fetcher` は Colab の外では
  止まるようにしてある。`KEIBA_ALLOW_LOCAL_FETCH=1` を設定してこれを外してはいけない
- **Colab でも大量に取らない。** 約2時間続けて取ったら Colab のIPも拒否された。
  再現評価は1回に数日分まで。過去の開催をまとめて何十日も取らない
- **Colab のセッションは使い終わったら止める**（`colab_remote.stop()`。`replay_day.py` は自動で
  止める）。止めないと compute units を消費し続ける。`colab sessions` で残っていないか確認する
- **秘密情報を `colab --env` やコマンドに書かない**（`~/.config/colab-cli/history` に平文で残る）
- **未来の情報を使わない。** 評価は `replay_day.py` を通して行う。このスクリプトはウェアハウスを
  その日の前で切ってから計算する。自分で別の方法を組むときも、評価する日以降の結果・オッズを
  特徴量に入れないこと
- **予想ロジックの数字（`flags.py` の境目・重み、`views.py` のリストの条件）を勝手に変えない。**
  評価の結果から変えたほうがよさそうなら、根拠（何レース・何頭で、どれだけ差があったか）を添えて
  提案にとどめる
- **コミットしないもの**: `data/shutuba/*_weekend.json`（予想の当日に使う出馬表）、
  `flop_explore.csv`（作業用）。コミットするのは `reports/` の下（md・csv・cards.json）と、
  頼まれて変えたコードだけ

## 結果の読み方

`reports/SUMMARY.md` の項目と、比べる相手：

| 項目 | 意味 | 比べる相手 |
|---|---|---|
| 目線の1番手が3着内 | その目線で一番評価の高い馬が3着以内に来た割合 | 1番人気（市場あり・市場の見込みはこれと同じくらいが普通） |
| ピックアップ（人気4番以下）の3着内率 | 指数(最高)と指数(近3走)のフラグが両方立った人気薄が3着以内に来た割合 | 同じ人気帯の「該当しない」馬。2025〜2026年の検証では 23.4%（市場の見込み 21.3%）、該当しない人気4番以下は約12% |
| 要注意（5番人気以内）の6着以下率 | 凡走点2.5以上の上位人気が6着以下に沈んだ割合 | 「該当しない」馬。2025〜2026年の検証では 45〜52% 対 31〜41%（凡走点が低いほど低い） |
| 凡走点・ピックアップ点ごとの成績 | 点数が高いほど、凡走・好走が増えているか | 点数の低い帯 |

注意：

- 1日（24レース）では数字が大きくぶれる。ピックアップ（人気4番以下）は1日30頭前後、
  要注意は1日15〜20頭しかいない。**判断は少なくとも数週（数百頭）たまってから**。
  それまでは「検証の数字と同じ向きか」だけを見る
- 新馬戦は過去の走りが無いので、指数・能力・対戦比較の目線もピックアップ・要注意も出ない
- オッズは確定オッズ。実際に予想するときは発走前のオッズなので、少しずれる
- 目線は「市場に何を足せるか」で選んである（`reports/prob_vs_deviation.md`、
  `scripts/views_eval.py`）。的中率が高くても市場と同じ馬を選んでいるだけの目線もある
  （前走パフォーマンス・能力）

## 報告の形

評価を頼まれたら、次をまとめて返す：

1. 対象の日付とレース数、`reports/SUMMARY.md` の合計の表
2. ピックアップ・要注意それぞれ「該当」と「該当しない」の差と、上の検証の数字と同じ向きか
3. 印象的な当たり・外れを数件（レース名、馬番・人気・点数・着順）
4. 数字が検証と大きく違う項目があれば、その指摘（ただし頭数が少ないうちは断定しない）
5. 変えたファイルと、コミット・push したか（頼まれたときだけ push する）
