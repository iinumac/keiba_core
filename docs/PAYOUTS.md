# 払戻データ

## なぜ別テーブルなのか

払戻は「レース単位」でも「馬単位」でもなく、**レース × 券種 × 組み合わせ**の単位。

- `results` は 馬×レース。馬連は2頭、三連複は3頭に紐づくので入らない
- `races` は 1レース1行。払戻は1レースに10行以上ある

`races` に列を足すと `tansho`, `fukusho1`, `fukusho2`, `fukusho3` … と横に伸び、
**同着が起きた瞬間に列が足りなくなる**。実データには3着が3頭同着で
ワイドが7組になったレースがある。横持ちだと作り直しになる。

```
data/warehouse/payouts/year=YYYY/part.parquet

  race_id        レースID
  bet_type       単勝 / 複勝 / 枠連 / 馬連 / ワイド / 馬単 / 三連複 / 三連単
  seq            同一券種内の連番（複勝の1〜3着、同着の各組を区別）
  combination    "12" / "2-12" / "2-9-12"（ハイフン区切りに正規化）
  horse_numbers  [2, 9, 12]（馬番のリスト。当たり判定に使う）
  payout         払戻金（100円あたり）
  popularity     人気
```

縦持ちなので、同着も複勝の着数変動も**行が増えるだけ**で吸収される。

## 実データのパターン（全57,810レースを走査）

実装前に全HTMLを走査して確認した結果。

### 発売されない券種がある

| 条件 | 発売なし | 該当 |
|---|---|---|
| 出走8頭以下 | **枠連** | 2,242レース |
| 出走4頭以下 | **複勝** | 1レース（2012-08-04 2歳新馬） |

> `races.horse_count` は出馬表時点の頭数で、出走取消があると実際とずれる。
> 枠連なしのレースに「9頭」が4件あるのはそのため。

### 同着で組数が増える

**組み合わせ数・払戻金額・人気の個数が食い違うレースは0件**だった。
パース時に個数が揃わない行は取り込まない実装にしてあるが、現状その発動はない。

| 券種 | 通常 | 例外 |
|---|---|---|
| 単勝 | 1 | 2組 78件（1着同着。2010年オークスなど） |
| 複勝 | 3 | **2組 861件**（7頭以下は2着まで）/ 4組 143件 / 5組 2件 |
| 枠連 | 1 | 2組 96件 |
| 馬連 | 1 | 2組 107件 |
| ワイド | 3 | 5組 144件 / **7組 2件** |
| 馬単 | 1 | 2組 185件 |
| 三連複 | 1 | 2組 144件 / **3組 2件** |
| 三連単 | 1 | 2組 329件 / 3組 2件 |

### 最も極端な例

**3着が3頭同着**したレースが2件ある。複勝5組・ワイド7組・三連複3組になる。

| | |
|---|---|
| `201208040611` | 2012-10-20 京都 室町ステークス（16頭） |
| `202009050712` | 2020-11-23 東京 3歳以上1勝クラス（18頭） |

横持ちスキーマがここで破綻する。

## 使い方

```sql
-- 三連複の配当分布
SELECT
  CASE WHEN payout < 1000 THEN '1. ~1000'
       WHEN payout < 5000 THEN '2. 1000-5000'
       WHEN payout < 50000 THEN '3. 5000-50000'
       ELSE '4. 50000~' END AS band,
  count(*) AS n, round(avg(payout)) AS avg_payout
FROM race_payouts
WHERE bet_type = '三連複'
GROUP BY 1 ORDER BY 1;
```

```python
# 買い目が当たったかの判定
from keiba import store
con = store.connect()
hits = con.sql("""
    SELECT race_id, combination, payout
    FROM payouts
    WHERE bet_type = '三連複' AND race_id = '202601010101'
""").df()
```

`race_payouts` ビューは `payouts` にレース属性（日付・競馬場・距離・頭数）を
結合したもの。通常はこちらを使う。

## 全レース買う前提をやめる

全レースを買うと毎回控除率を払うので、回収率は構造的に `100 - 控除率` に
収束する。モデルの上乗せが +4.3pt あっても、+22.5pt には届かない。

**買わないレースは回収率100%**（資金が減らない）。したがって勝ち筋は

1. 買うレースを選ぶ（参加率を下げる）
2. 買う点数を減らす
3. 残したレースで上乗せを稼ぐ

評価も「全レースの回収率」ではなく **「参加率」と「購入レースの回収率」**の組で見る。

### 絞り込みの効果（ワイド3点、検証5,712レース）

絞り込みは `edge3 = AI上位3頭の確率合計 − 同じ馬の市場暗示確率合計`。
**市場が見落としている度合い**が大きいレースから順に買う。

| 参加率 | 購入レース | 的中率 | 回収率 | 95%信頼区間 | 収支 |
|---|---|---|---|---|---|
| 100% | 5,712 | 55.6% | 81.8% | 79〜84 | −312,350円 |
| 48.7% | 2,784 | 67.6% | 86.3% | 83〜90 | −114,660円 |
| 23.5% | 1,344 | 74.3% | 89.7% | 85〜94 | −41,570円 |
| 8.8% | 500 | 79.6% | 91.5% | 85〜98 | −12,820円 |
| 4.2% | 238 | 80.3% | 90.5% | 81〜100 | −6,780円 |
| 0.7% | 39 | 89.7% | 97.6% | 77〜118 | −280円 |

絞るほど回収率も的中率も上がり、損失が縮む。ただし **95%信頼区間の下限が
100%を超えたものは一つもない**。回収率が100%を超えて見えるケースは
参加率1%未満（数十レース）で、区間は 90〜143 のように広く、
偶然と区別できない。

**数字の大小ではなく区間で判断すること。** 絞るほどレース数が減り、
「本当に勝てるか」の確認はかえって難しくなる。

## 戦略評価は的中率と回収率の両方で

`src/keiba/backtest.py` が両方を出す。

| 券種 | 選び方 | 点数 | 的中率 | 回収率 | 控除率後の基準 | 上乗せ |
|---|---|---|---|---|---|---|
| ワイド | AI | 3 | 55.6% | **81.8%** | 77.5% | +4.3pt |
| ワイド | 人気 | 3 | 55.7% | 81.1% | 77.5% | +3.6pt |
| 三連複 | AI | 10 | 36.0% | 76.6% | 75.0% | +1.6pt |
| 三連複 | 人気 | 10 | 35.7% | 74.0% | 75.0% | −1.0pt |
| 三連単 | AI | 60 | 36.0% | 73.2% | 72.5% | +0.7pt |
| 馬連 | AI | 3 | 31.9% | 76.9% | 77.5% | −0.6pt |

**最高配当1本の寄与はどれも0.2〜1.0%**で、これらの数字は外れ値に支配されていない。
つまり結論は安定している。

現状、**モデルの上乗せは最大 +4.3pt（ワイド3点）で、黒字には +22.5pt 必要**。
セグメントを切っても（市場との不一致、頭数、芝ダート）79〜82%で横ばいで、
明確な優位は見つかっていない。とくに「AI1位≠1番人気」のレースが
一致時を上回らないことが、モデルが市場に無い情報を持てていない証拠。

## 回収率を出すときの注意

- **同着は複数行**。1レースで複数の当たりが出るので、`SUM(payout)` が正しい
  （どれか1つではない）
- **払戻は100円あたり**。点数×100円が購入額
- **券種によっては発売されていない**。枠連を含む戦略を評価するときは
  8頭以下のレースを除くか、発売の有無を確認すること
